# Normalización de la Base de Datos

<!--
============================================================
DOCUMENTO: 05_normalization.md
============================================================

FUNCIÓN:
Analizar y documentar el proceso de normalización de la base
de datos para reducir redundancias, evitar anomalías y mejorar
la integridad de la información.

¿QUÉ ES LA NORMALIZACIÓN?
Es un proceso de organización de los datos mediante reglas
y formas normales que permiten estructurar correctamente
las relaciones de una base de datos.

¿POR QUÉ ES IMPORTANTE?
Una estructura mal organizada puede provocar:

- Duplicación innecesaria de información.
- Inconsistencias entre registros.
- Dificultades para actualizar datos.
- Pérdida accidental de información.
- Problemas al insertar o eliminar registros.

RELACIÓN CON LOS DOCUMENTOS ANTERIORES:

- 00_requirements.md: necesidades del cliente.
- 01_business-rules.md: reglas del negocio.
- 02_entities-and-attributes.md: entidades y atributos.
- 03_diagram-er.md: relaciones conceptuales.
- 04_relation-model.dbml: estructura lógica de las tablas.
- 05_normalization.md: análisis y justificación de la normalización.

IMPORTANTE:
La normalización debe realizarse sobre la estructura lógica
de los datos. No consiste en dividir tablas arbitrariamente.
Cada transformación debe estar justificada por las dependencias
entre los atributos y las reglas del negocio.

============================================================
CONCEPTOS FUNDAMENTALES
============================================================

REDUNDANCIA:
Almacenamiento repetido e innecesario de la misma información.

ANOMALÍA DE INSERCIÓN:
Problema que impide o dificulta registrar información
sin introducir datos adicionales que no deberían ser necesarios.

ANOMALÍA DE ACTUALIZACIÓN:
Problema que ocurre cuando un mismo dato está almacenado
en varios lugares y no se actualizan todos correctamente.

ANOMALÍA DE ELIMINACIÓN:
Problema que ocurre cuando al eliminar un registro se pierde
información que debería conservarse.

DEPENDENCIA FUNCIONAL:
Relación entre atributos donde el valor de uno o un conjunto
de ellos determina el valor de otro atributo.

Ejemplo:
student_id → student_name

Significa que, para cada student_id, existe un student_name
determinado dentro del contexto del modelo.

CLAVE CANDIDATA:
Atributo o conjunto mínimo de atributos que identifica
de forma única cada registro de una relación.

============================================================

## 3. Primera Forma Normal (1FN)

<!--
OBJETIVO:
Verificar que cada relación cumpla con los requisitos de la
Primera Forma Normal.

CRITERIOS PRINCIPALES:

- Cada celda contiene un valor individual.
- No existen grupos repetitivos de columnas.
- No se almacenan listas de valores dentro de una misma columna
  cuando estos valores deben tratarse como datos individuales.

  id integer
  name varchar

}

POSIBLE SOLUCIÓN:
Separar la información de cursos mediante una entidad relacionada

## 4. Segunda Forma Normal (2FN)

<!--
OBJETIVO:
Verificar que las relaciones cumplan con los requisitos
de la Segunda Forma Normal.

CRITERIOS PRINCIPALES:

- La relación debe cumplir previamente con 1FN.
- Cada atributo que no forma parte de una clave candidata
  debe depender de la clave candidata completa.
- No deben existir dependencias parciales respecto a una
  clave candidata compuesta.

¿QUÉ ES UNA DEPENDENCIA PARCIAL?
Ocurre cuando un atributo depende solamente de una parte
de una clave compuesta y no de la clave completa.

EJEMPLO:

Enrollment(student_id, course_id, student_name, course_name, grade)

Clave compuesta:
(student_id, course_id)

Dependencias:
student_id → student_name
course_id → course_name
(student_id, course_id) → grade

student_name depende solamente de student_id.
course_name depende solamente de course_id.

Por lo tanto, existen dependencias parciales.

POSIBLE SOLUCIÓN:
Separar la información en relaciones como:

Students(student_id, student_name)
Courses(course_id, course_name)
Enrollments(student_id, course_id, grade)

IMPORTANTE:
La 2FN es especialmente relevante cuando existen claves candidatas
compuestas. Una relación cuya clave candidata está formada por
un solo atributo no presenta dependencias parciales respecto
a esa clave.
-->

## 5. Tercera Forma Normal (3FN)

<!--
OBJETIVO:
Verificar que las relaciones cumplan con los requisitos
de la Tercera Forma Normal.

CRITERIOS PRINCIPALES:

- La relación debe cumplir previamente con 2FN.
- Los atributos no primos deben depender de una clave candidata,
  de toda la clave y de nada más que la clave.

¿QUÉ ES UNA DEPENDENCIA TRANSITIVA?
Ocurre cuando un atributo no primo depende de otro atributo
no primo, que a su vez depende de una clave candidata.

EJEMPLO:

Employees(employee_id, department_id, department_name)

Dependencias:
employee_id → department_id
department_id → department_name

Por lo tanto:
employee_id → department_name

El nombre del departamento depende de employee_id
a través de department_id.

POSIBLE SOLUCIÓN:

Employees(employee_id, department_id)
Departments(department_id, department_name)

IMPORTANTE:
La evaluación formal de 3FN debe considerar todas las claves
candidatas y las dependencias funcionales, no solamente
la clave primaria elegida.
-->

## 6. Forma Normal de Boyce-Codd (BCNF) — Revisión adicional

<!--
OBJETIVO:
Revisar si existen anomalías que todavía puedan presentarse
en relaciones que cumplen 3FN.

BCNF es una forma normal más estricta que 3FN.

CRITERIO:
Para toda dependencia funcional no trivial X → Y,
X debe ser una superclave.

Una superclave es un atributo o conjunto de atributos
que identifica de manera única cada registro.

¿CUÁNDO ES IMPORTANTE?
Existen relaciones que pueden cumplir 3FN y todavía presentar
dependencias funcionales problemáticas debido a varias claves
candidatas que se superponen.

IMPORTANTE:
No todos los proyectos necesitan transformaciones adicionales
a BCNF. Debemos analizar las dependencias y justificar
si se requiere o no.

## 9. Consideraciones de desnormalización

OBJETIVO:

¿QUÉ ES LA DESNORMALIZACIÓN?
Es la introducción controlada de redundancia u otras modificaciones
en una estructura normalizada para responder a necesidades
específicas del sistema.

EJEMPLOS:
- Almacenar valores agregados para evitar cálculos frecuentes.
- Mantener ciertos datos históricos aunque cambie la información
  original.
- Duplicar información seleccionada para optimizar consultas.

IMPORTANTE:
La desnormalización no debe utilizarse para corregir un mal diseño.
Debe existir una justificación técnica y mecanismos que mantengan
la consistencia de la información.

En un proyecto inicial puede no ser necesaria.
